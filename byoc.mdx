BYOC (Bring Your Own Cloud) allows you to deploy E2B sandboxes to your own cloud infrastructure within your VPC.

BYOC is available on AWS, Google Cloud (GCP), and Azure.

<EnterpriseBanner />

## BYOC is not self-hosting

BYOC and self-hosting are often conflated. They are different deployment models:

| | E2B Cloud | BYOC | E2B Embed (self-hosted) |
| --- | --- | --- | --- |
| Where sandboxes run | E2B's Google Cloud account | Your own AWS account, GCP project, or Azure subscription, inside your VPC | One Linux machine you operate: a host with KVM, a VM on GCP, AWS, or Azure, or a node in your Kubernetes cluster |
| Who provisions and monitors the cluster | E2B | E2B, using Terraform and machine images | You |
| Templates, snapshots and runtime logs stored in | E2B Cloud | Your VPC | The machine |
| Sandbox traffic and template build sources | E2B Cloud | Never leave your VPC | Never leave the machine |
| SDK, CLI and API | Same | Same | Same |
| How to get it | <a href="https://console.e2b.dev/sign-up?signup_source=docs_byoc" target="_blank" rel="noopener">Sign up</a> | [Contact us](mailto:enterprise@e2b.dev) | Install [E2B Embed](https://github.com/e2b-dev/runtime/tree/main/embed#readme) (Apache-2.0) yourself |

With BYOC you get a managed deployment inside your own cloud account. E2B provisions the cluster, monitors it, and creates a project under your E2B account, and you then use the same SDK, CLI, and API as you would against the E2B Cloud. Sandboxes themselves work identically, including [pause and resume persistence](/sandbox/persistence). Self-hosting means running [E2B Embed](https://github.com/e2b-dev/runtime/tree/main/embed#readme), the open-source runtime packaged for one machine, in which case operating that machine is your responsibility. Embed is a single-machine product; if you need to scale across machines, or want E2B to operate the deployment in your cloud account, that is BYOC.

## Architecture

Sandbox templates, snapshots, and runtime logs are stored within the customer's BYOC VPC.
Anonymized system metrics such as cluster memory and cpu are sent to the E2B Cloud for observability and cluster management purposes.

All potentially sensitive traffic, such as sandbox template build source files,
sandbox traffic, and logs, is transmitted directly from the client to the customer's BYOC VPC without ever touching the E2B Cloud infrastructure.

### Glossary
- **BYOC VPC**: The customer's Virtual Private Network where the E2B sandboxes are deployed. For example your AWS account, or the virtual network (VNet) in your Azure subscription.
- **E2B Cloud**: The managed service that provides the E2B platform, observability and cluster management.
- **OAuth Provider**: Customer-managed service that provides user and E2B Cloud with access to the cluster.

### BYOC cluster components
- **Orchestrator**: Represents a node that is responsible for managing sandboxes and their lifecycle. Optionally, it can also run the template builder component.
- **Edge Controller**: Routes traffic to sandboxes, exposes API for cluster management, and gRPC proxy used by E2B control plane to communicate with orchestrators.
- **Monitoring**: Collector that receives sandbox and build logs and system metrics from orchestrators and edge controllers. Only anonymized metrics are sent to the E2B Cloud for observability purposes.
- **Storage**: Persistent storage for sandbox templates, snapshots, and runtime logs. Image container repository for template images.

## Onboarding

Customers can initiate the onboarding process by reaching out to us.
Customers need a dedicated cloud account and need to know the region they will use.

- **AWS**: a dedicated AWS account. We receive the IAM role needed for managing account resources. Account quota limits may need to be increased.
- **Google Cloud**: a dedicated GCP project with billing enabled. You apply a Terraform module we provide, which creates the deployment service account E2B uses to manage project resources.
- **Azure**: a dedicated Azure subscription. You apply a Terraform module we provide, which gives E2B's provisioning application scoped access to that subscription. No credentials are exchanged. The person applying it needs the `Owner` role on the subscription and the `Cloud Application Administrator` role (or equivalent) in Microsoft Entra ID. Request vCPU quota for the VM sizes we confirm for your region early, because new subscriptions can take time to get quota approved.

Terraform configuration and machine images will be used for provisioning BYOC cluster.
When provisioning is done and running, we will create a new project under your E2B account that can be used by SDK/CLI the same way as it is hosted on E2B Cloud.

## FAQ

<AccordionGroup>
    <Accordion title="How is cluster monitored?">
    Cluster is forwarding anonymized metrics such as machine cpu/memory usage to E2B Control plane for advanced observability and alerting.
    The whole observability stack is anonymized and does not contain any sensitive information.
    </Accordion>
    <Accordion title="Can cluster automatically scale?">
    A cluster can be scaled horizontally by adding more orchestrators and edge controllers.
    The autoscaler is currently in V1 not capable of automatically scale orchestrator nodes that are needed for sandbox spawning.
    This feature is coming in the next versions.
    </Accordion>
    <Accordion title="Are sandboxes accessible only from a customer’s private network?">
    Yes. Load balancer that is handling all requests coming to sandbox can be configured as internal and VPC peering
    with additional customer’s VPC can be configured so sandbox traffic can stay in the private network.

    On Azure, the cluster exposes an internal load balancer, and you reach it from your own VNet by creating an Azure Private Link service and private endpoint in your subscription.
    </Accordion>
    <Accordion title="How control plane secure communication is ensured?">
    Data sent between the E2B Cloud and your BYOC VPC is encrypted using TLS.

    VPC peering can be established to allow direct communication between the E2B Cloud and your BYOC VPC.
    When using VPC peering, the load balancer can be configured as private without a public IP address.
    </Accordion>
</AccordionGroup>
